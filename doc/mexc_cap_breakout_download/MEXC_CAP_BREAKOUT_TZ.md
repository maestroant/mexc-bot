# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## MEXC — ТОРГОВЛЯ ПРИ СНЯТИИ ЦЕНОВОГО ПОТОЛКА

**Два алгоритма входа: FAST BREAKOUT и CONFIRMED BREAKOUT.** Полная цепочка от обнаружения ограничения до финальной сверки сделки; расчёт проскальзывания; управление TP1/TP2; защита общего PnL после любых частичных продаж; аварийные выходы; REPLAY/PAPER/LIVE.

**Статус:** проектное ТЗ, исходные пороги для тестирования. Не является подтверждением доходности. **В LIVE для одного события работает только один выбранный алгоритм; REPLAY сравнивает оба независимо.**

> **Основной принцип:** обнаружение снятия потолка ≠ команда BUY; касание TP ≠ полученная прибыль; целевая цена стопа ≠ гарантированная цена исполнения. Решение принимается по целостным рыночным данным, реальным ордерам и полной экономике позиции.

## 1. Область действия, допущения и ожидаемый результат

Задача — добавить независимый торговый сценарий к существующему боту листингов. Не переписывать основную логику нового листинга: она может работать отдельно, но CAP-стратегия должна видеть занятость позиции/ордеров того же символа и разделять общий лимит риска. Переиспользовать расчёт стакана, вход aggressive LIMIT, исполнение/сверку ордеров, TP/BE/time-stop, срочный LIMIT SELL и проектный аварийный `RequestSellOrderMinPrice()`.

**Факты из предоставленных материалов:** для некоторых изученных листингов наблюдалось ограничение примерно первые 10 минут; отказ реальной заявки с кодом `30010` содержал конкретный максимальный уровень цены (пример LALA); положительный `/api/v3/order/test` не подтверждал фактическую возможность исполнения выше потолка. Длительность 600 с — подсказка **только** для пар с подтверждённым таким режимом. Цена выше потолка в ask сама по себе не означает снятие ограничения.

**Проектные решения, подлежащие тестам:** два набора входа, длительность окон, резерв на ухудшение ликвидности, защитный целевой общий PnL, временные и ценовые параметры. Их нельзя выдавать за подтверждённые рыночные закономерности.

Результат разработки: детерминированный REPLAY, PAPER и (после отдельного разрешения) LIVE; один детектор, два независимых EntryEngine, общий OrderReconciler, общий PositionManager; полные причины каждого решения, включая SKIP.

## 2. Термины и модель данных

| Термин / поле | Точное значение |
|---|---|
| `capPrice` | Биржевой верхний предел цены, подтверждённый для данной пары и временного интервала; НЕ наш LIMIT-лимит покупки. |
| `capEvidence` | Источник, время и сырой ответ, например отказ `30010` с извлечённым capPrice. Не создавать торговые пробные заявки только ради ошибки. |
| `releaseCandidate` | Первая подтверждённая реальная сделка по цене `>= capPrice + priceStep`, но качество стакана ещё проверяется. |
| `releaseTime` | Время первого подтверждения `CAP_RELEASED`, отдельно хранить биржевое время сделки, время получения и время принятия решения. |
| `releaseEventId` | Уникальный идентификатор (symbol + listingId + capPrice + событие), защищающий от повторной покупки. |
| `marketHealthy` | Последовательности стакана без разрывов, актуальные bid/ask, торговый статус пары, корректные фильтры и метки времени. |
| `entryPriceCap` | Максимальная допустимая цена собственного aggressive LIMIT BUY, `floorStep(bestAsk*(1+entryOffsetPct/100))`. |
| `exitVWAP(qty)` | Расчётная цена исполнения продажи `qty` через текущие bids с учётом их фактических объёмов. |
| `buyVWAP(qty)` | Расчётная цена агрессивной покупки `qty` через asks, ограниченная `entryPriceCap`. |
| `Q` | Фактический доступный остаток базового актива после BUY/SELL и удержанных комиссий в базовой валюте. |
| `C` | Полная стоимость фактически купленного доступного количества, включая приведённые к USDT комиссии покупки. |
| `R` | Полученная выручка по фактически исполненным SELL за вычетом приведённых к USDT комиссий SELL. |
| `P_BE`, `P_LOCK` | Расчётные минимальные цены выхода остатка для результата всей сделки 0% или целевой прибыли. |
| `slippageStressPct` | Дополнительный стресс-буфер к будущему `exitVWAP`, не повторяющий уже учтённую глубину/спред. |

Один `symbol` → единый ledger: trade fills BUY/SELL, комиссии с валютой, активные/отменяемые ордера, подтверждённый остаток, триггеры, snapshot-ы и идентификаторы решений. Использовать десятичную арифметику (`Decimal`), не binary float для цены и количества.

## 3. Общий детектор и действия ДО выбора A/B

### 3.1. NEW LISTING → MARKET READY

1. Получить символ, статус пары, время начала, precision/`priceStep`/`qtyStep`, `minQty`, `minNotional`, комиссии, балансы и доступность API.
2. Подключить публичные WebSocket-сделки, bestBid/bestAsk и diff-depth; через REST snapshot построить локальный стакан согласно биржевой последовательности обновлений. Подписаться на приватные order/fill события, обеспечить REST-сверку.
3. Если некорректная последовательность, остановка WS, возраст стакана выше допустимого или несогласованные данные — `BOOK_RECOVERY`; новые BUY запрещены. Если позиция открыта — состояние риска и сверку ордеров вести независимо.
4. Начать непрерывное логирование рыночных событий — независимо от того, был ли вход.

### 3.2. CAP CONFIRMATION → WAIT RELEASE

1. Принять `capPrice` только из обоснованного источника, например из уже возникшего отказа `30010`, содержащего числовой максимум. Проверить пару, единицы, временную актуальность, сохранить оригинальную причину.
2. Если доказательства нет — `OBSERVE_ONLY`. Флэт цены и успех `/order/test` не являются доказательством потолка или его отмены.
3. При известном ожидаемом T+600 повысить частоту локальной аналитики заранее; само время не снимает ограничение.
4. Каждую сделку проверить: `symbol` совпадает, реальное исполнение, `tradePrice >= capPrice + priceStep`. Если да — `RELEASE_CANDIDATE`; сохранить исходное событие. Затем проверить свежий согласованный стакан и `bestBid >= capPrice + priceStep`. Если да — **один раз** `CAP_RELEASED`, запомнить `releaseTime`.
5. Если bid ещё ниже или данные повреждены — ждать и восстанавливать, **не покупать**. Обязателен абсолютный дедлайн окна входа, основанный на реальном времени и валидности информации; событие не воспроизводится задним числом.

### 3.3. Общий арбитр

- В `LIVE`: `activeEntryMode=FAST` **или** `CONFIRMED` **или** `DISABLED`; переключение алгоритма после неудачной попытки на том же `releaseEventId` запрещено.
- В `REPLAY`: обе ветки исполняются на одинаковой ленте рыночных событий в изолированных виртуальных счетах; контрольная ветка NO TRADE.
- При существующей позиции/активном BUY/неизвестном SELL по символу — `SKIP_CONFLICT`; один release не может создавать дубль.
- В каждом решении записать причину отказа каждого фильтра, не только итог YES/NO.

## 4. Общие расчёты входа и защиты от проскальзывания

### 4.1. Размер позиции и цена

`entryPriceCap = floorToStep(bestAsk * (1 + buyAggressiveCapPct/100), priceStep)`

`plannedQty = floorToStep(orderUSDT / entryPriceCap, qtyStep)`

`estimatedMaxCost = plannedQty * entryPriceCap <= orderUSDT`

`releaseReferenceAsk` = первый синхронизированный bestAsk после события CAP_RELEASED. `chasePct = 100×(bestAskAtDecision / releaseReferenceAsk − 1)`. Отказ, если `chasePct > maxChasePct` (стартовая **тестовая гипотеза** 20%; сравнить 10/20/40%). Значение anchor фиксируется один раз на release, не подменяется новым максимумом.

**Проверить до BUY:** `minNotional`, минимальное количество, step, дневной/символьный риск и доступный баланс. BUY не «догоняет» ask путём повышения лимита после отправки. Для нового решения после изменения стакана выполняются все проверки заново и лишь до разрешённого дедлайна.

### 4.2. Четыре составляющих качества сделки

1. **Spread**: `100*(bestAsk-bestBid)/midPrice`.
2. **Глубина и плановый VWAP BUY**: проход asks вплоть до `entryPriceCap`, не больше запрошенного объёма. Если объём не помещается — уменьшить qty с проверкой минимального ордера или SKIP; не принимать исполнение далеко за пределами цены.
3. **Плановый VWAP SELL**: пройти bids для **всего предполагаемого фактически купленного количества**, включая очередность и доступный объём. Если полного покрытия нет — BUY запрещён.
4. **Stress buffer будущей продажи**: отдельная добавка, отражающая ухудшение между snapshot и исполнением. Не вычитать spread/текущую глубину дважды: они уже отражены в `exitVWAP`.

### 4.3. Измерение проскальзывания, комиссии и оценка входа

- Ожидаемая стоимость BUY: `plannedQty * buyVWAP`; худшая разрешённая цена BUY — `entryPriceCap`.
- Ожидаемая стоимость SELL сразу после BUY: `plannedQty * exitVWAP` минус комиссия; затем применить stress к **будущему** исполнению.
- `actualBuySlippagePct = 100*(avgBuyFillPrice - bestAskAtSend)/bestAskAtSend`. Расстояние до bestAsk не следует путать с размером спреда.
- `actualSellExecutionGapPct = 100*(actualAvgSellPrice - expectedExitVWAPAtSend)/expectedExitVWAPAtSend` (отрицательно — хуже ожидания).
- `stressExitValue = Q * exitVWAP(Q) * (1 - sellFeeRate) * (1 - slippageStressPct/100)` для риск-сценария после учёта доступных bids.
- **Перед BUY** проверить стрессовый round-trip результат и максимальный допустимый worst-case loss в USDT. `EntryStressLossPct = 100×(stressedImmediateExitValue−plannedMaxBuyCostWithFee)/plannedMaxBuyCostWithFee`; для допуска `EntryStressLossPct >= −maxEntryStressLossPct` (исследовательский старт: 3%, сравнить 1/3/5%; при отсутствии полного exitVWAP — отказ). Отрицательная величина — допустимый гипотетический убыток немедленного round-trip, **не гарантированный stop-loss**. Пороги по A и B независимы.

Если цена/время снимка, от которого отправлен ордер, неизвестны — slippage пометить `UNMEASURABLE` и сделку исключить из чистой оценки по качеству исполнения, но **не** исключать из PnL.

## 5. Алгоритм A — FAST BREAKOUT: пошаговые действия

**Цель:** найти первый пригодный к исполнению вход в коротком окне после `CAP_RELEASED`, не ожидая дополнительной стабильности стакана. Быстрый ≠ безусловный. Только одна отправленная BUY-попытка.

| Шаг | Триггер / условие | Действие бота | НЕТ / ошибка |
|---|---|---|---|
| A1 | `CAP_RELEASED` | Задать `deadline=releaseTime+10s`, `decisionId`; запретить повторные идентичные события. | Дубликат → игнорировать. |
| A2 | Новое согласованное состояние стакана; `bookAge<=250ms` (стартовый порог) | Прочитать bid/ask, 20+/полную локальную глубину, время и активность. | BOOK_RECOVERY / ждать следующего события до дедлайна. |
| A3 | `spread<=maxSpread`, bid выше cap, запас bids/asks, оценимый полный exitVWAP | Рассчитать buyVWAP/exitVWAP, комиссии и стрессовый PnL. | Не купить; продолжать скан в пределах 10s. |
| A4 | Качество входа и stop-risk допустимы | Проверить исчезновение bids, короткий ценовой разворот, скорость роста и ограничение chase. | Сохранить SKIP_REASON и продолжать до deadline. |
| A5 | Котировки ещё годны непосредственно перед отправкой | Вычислить `entryPriceCap` и qty, проверить minNotional и остаточный риск. | Пересчёт по новому стакану, не повышать price cap вслепую. |
| A6 | Сработал `ENTRY_ALLOWED` | Послать один `LIMIT BUY` с уникальным clientOrderId. | Таймаут создания → `ORDER_UNKNOWN`, только REST/WS-сверка. |
| A7 | BUY fill пришёл до `buyFillTimeoutMs=1200ms` либо срок истёк | Запросить реальные fills, отменить неполученный остаток, дождаться подтверждения. | 0 fills → SKIP, не повторять BUY. |
| A8 | `filledQty>0` и остаток BUY отменён/известен | Открыть позицию на фактическую доступную qty; вычислить avgBuyPrice, все комиссии. | Если qty ниже биржевого минимума SELL — `DUST_RISK`, аварийная процедура/эскалация без выдуманной ликвидации. |
| A9 | Позиция готова | Передать её в общий PositionManager; выставить допустимые TP. | Не ставить TP, которые нарушают minNotional или зарезервированный qty. |
| A10 | Истёк deadline без ордера | `SKIP_FAST_WINDOW_END`, сохранить полную ленту. | Завершить событие без B-автоподмены. |

**Профиль FAST для первичной проверки:** окно 10s; maxBookAge=250ms; фильтры исходной стратегии (в первую очередь spread<=1.2%, bid07>=15×, bid15>=30×, ask07>=8×, estimatedExitSlippage<=1.5%), без обязательной стабилизации; отдельный стресс-буфер для SELL. Возможное ослабление допускается **только** в исследованиях с отдельными метками профилей, не автоматически в LIVE.

## 6. Алгоритм B — CONFIRMED BREAKOUT: пошаговые действия

**Цель:** отфильтровать кратковременные ложные изменения стакана, дождаться устойчивого состояния, не гнаться за ценой. Вход не гарантируется даже при резком росте.

| Шаг | Триггер / условие | Действие бота | НЕТ / ошибка |
|---|---|---|---|
| B1 | `CAP_RELEASED` | `deadline=releaseTime+30s`, `stableSince=null`, `distinctUpdates=0`. | Дубликат → игнорировать. |
| B2 | Пришёл новый валидный WS diff-depth / bookTicker | Проверить sequence, bookAge<=500ms, торговый статус и срок окна. | Gap → `BOOK_RECOVERY`, обнулить стабильность. |
| B3 | Одновременно пройдены все строгие входные фильтры | Запустить или продолжить непрерывный период допустимости. | Любой фильтр false → stableSince=null, updates=0. |
| B4 | Условия сохранялись >=200ms и прошло >=3 **различных** обновления | `ENTRY_ALLOWED_CANDIDATE`, заморозить ссылку на snapshot. | Продолжать проверять до 30s. |
| B5 | Нет chase/spike reversal, подтверждены bids и стрессовый PnL | Рассчитать buyVWAP, `entryPriceCap`, qty. | Вернуться B2 до deadline либо SKIP на запрете риска. |
| B6 | Финальный pre-send recheck на новом snapshot true | Единственный `LIMIT BUY` с clientOrderId. | false → B2 без размещения ордера. |
| B7 | До 1200ms fill или timeout | Cancel unfilled → reconcile fills, позиции только по факту. | 0 fills → SKIP, не повторять BUY. |
| B8 | `filledQty>0`, статус известен | Общий PositionManager + TP/stop и slippage logs. | Дубликаты запрещены. |
| B9 | 30s истекли раньше первого BUY | `SKIP_NO_STABLE_ENTRY`. | Вход после дедлайна запрещён. |

**Что именно называется стабильностью:** фильтры непрерывно true на каждом валидном обновлении в интервале, без sequence gap; одновременно >=3 уникальных `bookVersion`/события и >=200ms времени. Серия искусственных локальных пересчётов без новых данных **не** засчитывается как три обновления. В B те же строгие пороги ликвидности и проскальзывания, что в базовой торговой логике; дополнительные пороги не считаются доказанными.

## 7. Общая позиция: учёт всех исполнений и TP

1. Сразу после BUY создать immutable fill-ledger. `Q = netBoughtBase - soldBase`; при комиссии покупки в монете `netBoughtBase` уменьшается на эту комиссию. Стоимость C учитывает приведённую к USDT комиссию. Проверить резервирование средств, minimum quantity/precision.
2. План TP1: +2% от фактического среднего BUY на 50% **реально доступной** qty; TP2: +4% на остаток. Это существующий стартовый сценарий, а не оптимум. Для малой позиции (например, 10 USDT) TP1 на 5 USDT может не пройти minNotional — тогда использовать заранее утверждённый одноэтапный exit-профиль или пропустить сделку до BUY; нельзя молча создавать недопустимые заявки.
3. Если одновременно выставлены TP1 и TP2, зарезервированные qty в сумме `<= Q` после округления; менеджер отслеживает любые fills обеих заявок. Событие «достигнута котировка TP» не означает исполнение, только private fill меняет R и Q.
4. При любом частичном SELL пересчитать `R`, `Q`, `C`, `exitVWAP(Q)`, оценочную и стрессовую полную доходность; после каждой сделки перепроверить остаточные активные TP.
5. Один менеджер выхода владеет sell-lock: при триггере срочного выхода он замораживает создание новых TP, отменяет существующие, сверяет одновременно пришедшие fills, определяет остаток и только после этого отправляет срочный SELL.
6. При Q=0, но есть неразрешённые SELL → `RECONCILE`, пока нет подтверждённых состояний. Закрытие считается успешным только при известной истории ордеров и полном балансе.

## 8. Формула прибыли всей сделки при частичных продажах

**Только на основе фактических fill-ов:**

`C = Σ(buyFillPrice_i × buyFillQty_i) + Σ(buyFeeQuoteEquivalent_i)`

`R = Σ(sellFillPrice_j × sellFillQty_j) − Σ(sellFeeQuoteEquivalent_j)`

`Q = Σ(buyBaseQtyAfterBaseFee_i) − Σ(sellBaseQty_j) − Σ(baseFeeOnSell_j)`

`RealizedTradePnL_USDT = R − C`, **только когда Q=0**. Пока Q>0 эта величина не является результатом всей сделки.

`ProjectedFullPnL_USDT = R + Q×exitVWAP(Q)×(1−futureSellFeeRate) − C`

`StressedFullPnL_USDT = R + Q×exitVWAP(Q)×(1−futureSellFeeRate)×(1−slippageStressPct/100) − C`

`ProjectedFullPnL_Pct = 100×ProjectedFullPnL_USDT / C` (аналогично `StressedFullPnL_Pct`). Реализованный PnL можно раскрывать по лотам для аналитики, но защитные решения должны опираться на **всю исходную стоимость C** и все полученные R, а не на прибыль TP1 отдельно.

Для `Q>0` цена продажи оставшегося объёма, обеспечивающая целевую прибыль `targetFullPnLPct` **при исполнении по этой цене**, равна:

`P_target = [C×(1+targetFullPnLPct/100) − R] / [Q×(1−futureSellFeeRate)]`

С запасом на дополнительное ухудшение исполнения `s=slippageStressPct/100` требуемый сейчас `exitVWAP`:

`requiredExitVWAP = P_target / (1−s)`.

Если `Q=0`, формулы цены не применяются — считать окончательный netPnL. Если остаток не помещается в bids, `exitVWAP` недоступен и защита **не считается выполненной**.

**Не удваивать затраты:** текущий spread + ожидаемое влияние глубины уже вошли в `exitVWAP`; `slippageStressPct` покрывает только дополнительное изменение после снимка. Комиссии, удержанные биржей в MX или base, сначала нормализовать по фактической оценке, хранить и исходную валюту.

## 9. Сценарии TP1 исполнен, TP2 не исполнен

| Реальное состояние | Что делает бот |
|---|---|
| TP1 исполнен полностью, TP2 стоит и стакан ликвиден | Обновляет R/Q и удерживает TP2, но на каждом новом событии считает стрессовый общий PnL. |
| TP1 исполнен на 20 монет вместо плановых 50 | Фиксирует только 20 fill; R увеличивается на фактическую выручку; Q уменьшается лишь на 20; отмена/защита учитывает оставшиеся 80. |
| TP1 частичен одновременно со стоп-сигналом | Установить exit-lock; cancel TP1/TP2 → дождаться/сверить fills → срочный SELL только на оставшийся Q. |
| TP2 не исполняется, целевой PnL всей сделки под угрозой | `TOTAL_PNL_PROTECT`: отменить TP2 и другие SELL, сверить, отправить срочную продажу доступного остатка. |
| Вышел TP1 и последовал резкий обвал / исчезновение bids | `HARD_STOP/FAST_DROP/DEPTH_DISAPPEARED` имеют приоритет над мягким target; инициировать аварийную процедуру, без обещания сохранения прибыли. |
| TP2 частично исполнился сам | Немедленный пересчёт Q, R, комиссий и уровней; если Q=0 — конечная сверка. |
| Остаток ниже биржевого минимума SELL | `DUST_REMAINDER`, зафиксировать неизвлечённый остаток; нельзя маркировать сделку полностью закрытой или бесконечно создавать ошибки. |

### 9.1. Когда включать Total Position PnL Protection

- Защита включается после **первого реального положительного частичного SELL** (`partialProfitRealized=true`). Уровень целевой общей прибыли конфигурируется: для теста `targetFullPnLPct=0` или `+0.5%`; это не гарантированный lock-in.
- На каждое валидное обновление стакана пересчитывается `StressedFullPnL_Pct`. Если `<= targetFullPnLPct` — `TOTAL_PNL_PROTECT`, перейти в срочный выход (после cancel/reconcile). Если до этого защитный уровень ещё никогда не был достижим, ставить метку `PROTECTION_UNATTAINABLE` и выбирать заранее заданную политику: `EXIT_NOW` (консервативный профиль) либо `ALLOW_UNTIL_HARD_STOP` (только тест). Нельзя заявлять, что прибыль защищена.
- При положительной достигнутой общей прибыли можно установить повышаемый `lockedTargetPct` (не понижать при откате), но отдельный режим TRAILING требует REPLAY-валидации. По умолчанию не включать динамическое поднятие сверх установленного target.
- Если TP1 и TP2 получены полностью, не отправлять защитный SELL. Если данные плохие — не брать вымышленный exitVWAP: сначала оценить аварийность и восстановить ордерную картину.
- **Всегда старше protection:** потеря контроля над позицией / неизвестные ордера, hard stop, быстрое падение, исчезновение bids. Целевой PnL — решение начать продажу, а не лимит допустимого реального убытка.

### 9.2. Пример: TP1 успешен, а сделка убыточна

Допущения для примера: покупка `100×0.100 = 10.00 USDT`, buyFee=0.1% в USDT, TP1 `50×0.102=5.10`, sellFee=0.1%, осталось `50` монет. Тогда `C=10.01`, `R=5.0949`, `Q=50`.

Без будущего stress: `P_BE=(10.01−5.0949)/(50×0.999)=0.0984004` USDT. Если стресс на остаток 0.5%, `requiredExitVWAP≈0.098895` USDT. При продаже остатка по 0.095: чистая выручка от него `4.75×0.999=4.74525`; итог `PnL=(5.0949+4.74525−10.01)/10.01×100≈−1.70%`. TP1 +2% **не сделал сделку прибыльной**.

Если TP1 исполнился только на **20** монет по 0.102, `R=2.03796`, `Q=80`; новый `P_BE=(10.01−2.03796)/(80×0.999)≈0.0997503` USDT. То есть частично исполненный TP1 даёт **гораздо меньше запаса** для остальной позиции, чем полностью выполненный TP1.

## 10. Менеджер выходов: приоритет, триггер, действия

| Приоритет | Триггер | Конкретное действие |
|---|---|---|
| 0 | Неизвестный статус ордера / потенциально дублирующий SELL | `RECONCILE_ONLY`: блокировать новые конфликтующие заявки, получить статус и fills. |
| 1 | `HARD_STOP` (старт −8% нетто), `FAST_WINDOW_DUMP` (−6% за 1 c), `DEPTH_DISAPPEARED`, биржевой отказ дальнейшего выхода | `EXIT_URGENT`; при необходимости ускоренная аварийная ветка. |
| 2 | `FAST_DROP_STOP` (−2.5% в первые 3с), `BREAK_EVEN_STOP` (после MFE+1.5%, уровень +0.15%), сильное ухудшение качества ликвидности | `EXIT_URGENT`. |
| 3 | После реального частичного положительного SELL: `StressedFullPnL_Pct <= targetFullPnLPct` | `TOTAL_PNL_PROTECT` → `EXIT_URGENT`. |
| 4 | `TIME_STOP_NEGATIVE` (3с и ниже −0.3%), `TIME_STOP_NO_EDGE` (5с), `TIME_STOP_NO_MOMENTUM` (8с), `MAX_HOLD` (15с) | `EXIT_URGENT`. |
| 5 | Фактический TP1/TP2 fill | Ничего не продавать дополнительно; обновить ledger и цели, если Q=0 → проверить CLOSED. |

Время отсчитывать от первого фактического BUY fill, а **не** от старта листинга или выставления BUY. После частичных TP контроль максимального времени не сбрасывается. `netPnL` для проверок после частичных продаж — общий стрессовый/расчётный результат позиции, а параллельно отдельно хранить netPnL remaining leg, чтобы сохранить анализ поведения базовых стопов. Порог −8% применить к **общей позиции** в итоговой новой стратегии; не путать с −8% для остатка. Это осознанное новое правило, сравнить в REPLAY с «stop только по remaining leg».

## 11. Срочный и аварийный SELL: строгая последовательность

1. Атомарно включить `exitInProgress`; запретить новые BUY/TP/Sell-конкуренты.
2. Запросить отмену всех активных TP по их ID; получить ACK, затем сверить open orders/статусы и **все** fills, которые могли произойти в гонке с отменой.
3. Пересчитать Q и доступный актив; если Q=0 → `CLOSED` после сверки. Если есть статус UNKNOWN — `RECONCILE_ONLY`, а не новая SELL.
4. Если bids существуют — вычислить `sellLimitPrice=floorStep(bestBid×(1−sellAggressiveCapPct/100))`, исходно offset=0.5%, и отправить один aggressive LIMIT SELL на допустимый Q. При необходимости определить доступный объём SELL с учётом dust/minNotional.
5. Ждать до `exitOrderTimeoutMs=400ms` либо private fill. Если partial — учесть исполненное. При остатке: cancel + confirm + новые fills + актуальный стакан + новая цена. Максимум 3 контролируемых перестановки.
6. При исчезновении ликвидности, hard stop или исчерпании перестановок — после безопасной сверки перейти к **существующей веб-функции** `RequestSellOrderMinPrice()` (проектный fallback, не официальный тип MARKET). Её механизм зависит от поведения веб-формы и требует отдельных интеграционных тестов; никогда не считать её гарантией исполнения.
7. Если timeout/API unknown, не повторять ордер вслепую. Сначала выяснить, был ли он принят и исполнен частично. Для всех попыток сохранять `clientOrderId`, `orderId`, fills и остаток.
8. При невозможности продать — `RESIDUAL_OPEN / MANUAL_REVIEW`, лог, уведомление оператору. `CLOSED` допустим только при Q=0, отсутствии конфликтующих активных SELL и известном фактическом PnL.

## 13. Псевдокод решающего автомата

```text
onListing(symbol):
  initMarketStreamsAndLedger(symbol)
  while noCapEvidence: OBSERVE_ONLY
  while not releaseConfirmed:
    t = nextValidatedTrade()
    if t.price > capPrice and healthyBook().bestBid > capPrice:
       emitOnce(CAP_RELEASED)

onCapReleased(event):
  mode = liveEntryMode  # must be fixed before event
  if conflictOrUnknownOrder: SKIP_CONFLICT; return
  if mode == FAST: scanUntil(event.time + 10s, requireStable=false)
  if mode == CONFIRMED: scanUntil(event.time + 30s, requireStable=true)

scanUntil(deadline, requireStable):
  for each new validMarketEvent before deadline:
     if !marketHealthy: resetStable(); continue
     evaluateSpreadDepthBuyVWAPExitVWAPAndStress()
     if !filtersPass: resetStable(); continue
     if requireStable and (!200msContinuouslyGood or !3DistinctUpdates): continue
     if !preSendRecheck: continue
     sendOneLimitBuyWithId(); reconcileBuyAndCancelUnfilled()
     if actualFilledQty > 0: manageActualPosition()
     return
  recordSkipReasonAndNoBuy()

manageActualPosition():
  ledger = actualFillsAndFees()
  placeValidatedTPOrdersOrApplySmallPositionPolicy()
  while ledger.Q > 0:
     applyPrivateFillsAndReconcileOrders()
     projected = R + Q*exitVWAP(Q)*(1-sellFee)
     stressed  = R + Q*exitVWAP(Q)*(1-sellFee)*(1-stress) - C
     if anyCriticalStop or anyTimeStop:
        urgentExit(cancelReconcileTPThenSellRemaining()); continue
     if positivePartialSellExists and stressed <= C*targetFullPnLPct/100:
        urgentExit(cancelReconcileTPThenSellRemaining()); continue
     awaitNextMarketOrPrivateEvent()
  reconcileAllOrdersAndFinalizePnL()
```

Псевдокод намеренно сокращён: учитывать обязательную обработку `UNKNOWN`, недостаточного depth и недопустимого остатка — см. разделы 7–11. Применение реальных fill-ов выполняется перед оценкой триггеров каждого шага; сравнение денежного `stressed` с денежным `C*target/100` эквивалентно проверке `StressedFullPnL_Pct <= target`.

## 14. Исключительные случаи и инварианты

| Событие | Обязательное поведение |
|---|---|
| Подтверждения cap нет | Только мониторинг; CAP BUY запрещён. |
| T+600 наступило, но реальных сделок выше cap нет | Ждать подтверждения; время не торгует. |
| `order/test` успешно | Никакого CAP_RELEASED на основании тестового endpoint. |
| Стакан изменился без согласованных версий | `BOOK_RECOVERY`; новые BUY остановлены. |
| Fast пролетел цену, пока проверял фильтры | Ограничение chase; SKIP; не поднимать LIMIT «до рынка». |
| Confirmed получил только 1 хороший snapshot | Нет стабильности — нет BUY. |
| Timeout BUY/SELL и неизвестен ответ | RECONCILE_ONLY; никаких слепых дублей. |
| BUY partial, затем cancel | Позиция = только реальные fills, не заказанная qty. |
| Частичный TP1; TP2 открыт; срабатывает hard stop | Отменить и сверить оба TP; продать только новый Q. |
| TP1 в плюс, TP2 в минус | Итог считать по ВСЕМ sells и fees, не считать win на основании TP1. |
| Нет bids / невозможно рассчитать `exitVWAP` | Автоматически не маркировать прибыль как защищённую; аварийная стратегия и остаток на учёте. |
| TP leg ниже `minNotional` | До BUY пропустить/сменить предварительно утверждённый профиль; после BUY эскалация для dust. |
| Двойные fills/повтор WS событий | Идемпотентная дедупликация по ID исполнения. |
| Статус позиции неизвестен при падении сети | Синхронизация баланса, fills, order statuses до новых заявок. |
| CAP release не произошло в окно наблюдения | Завершить без BUY, сохранить market data и причину. |

**Инварианты:** `Q>=0` с точностью до правил учёта комиссий; сумму активных зарезервированных SELL не превышать доступный Q; по одному подтверждённому release не более одной BUY-попытки; ни один cancel/retry не оставляет неучтённый UNKNOWN; ни одна сделка не считается закрытой по свечке или предполагаемой цене.

## 15. Логи, сравнение FAST / CONFIRMED и тесты

**Логировать:** полученные/биржевые timestamps, market sequence/version, cap evidence и release proof, каждое пройденное/проваленное условие и причину SKIP, время принятия решения, latency, sent/ack/fill/cancel/unknown, priceStep и qtyStep, minNotional, bestBid/ask на отправке, buyVWAP/exitVWAP, spread, depth, комиссии по валютам, частичные TP, полный PnL, stress PnL, `P_BE`, `P_LOCK`, execution gap, MFE/MAE и остаток. Хранить сырые WS-данные, чтобы воспроизведение было детерминированным.

**Сравнить три портфеля:** FAST, CONFIRMED и NO TRADE. На каждый листинг отмечать: была ли доказана cap; было ли подтверждено release; был ли кандидат BUY; был ли fill; прибыль по всей закрытой сделке; непогашенный остаток; worst-case mark-to-exit; max drawdown; комиссии и реалистичное проскальзывание. Если сделок нет — не считать это убыточной торговой сделкой, но учитывать охват листингов.

**Моделирование latency:** отдельно задержка получения WS, вычислений, REST подачи, ACK, cancel, private fills; сценарии 20/50/100/200/500ms плюс хвостовые задержки. Не засчитывать исполнение только по касанию bestBid/ask: учитывать доступную глубину в момент доставки ордера, возможные изменения и очередь. Без данных очереди явно маркировать модель как приближённую и применять консервативный fill-rate.

**Обязательные тест-кейсы:**

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| T01 | 30010 есть; прошло 600с, реальных сделок выше cap нет | WAIT_RELEASE, нет BUY. |
| T02 | Первый trade выше cap; bestBid ниже cap | RELEASE_CANDIDATE, нет BUY. |
| T03 | A: первый snapshot слишком широк, следующий качественный в 10s | BUY только на валидном обновлении, не раньше. |
| T04 | B: хорошие условия менее 200ms или только 2 обновления | BUY нет; stable counter сбрасывается при провале. |
| T05 | B: 200ms/3 updates пройдены, pre-send стакан стал плохим | Возврат в scan, нет ордера. |
| T06 | Partial BUY 30%, cancel остатка | Менеджер работает на 30%; повторного BUY нет. |
| T07 | BUY/SELL timeout, но ордер фактически исполнен | Reconcile обнаруживает fill; запрет дубля. |
| T08 | TP1 заполнено 50%, TP2 не исполнено и цена падает | Защита общей сделки, лимит риска, exit остатка. |
| T09 | TP1 заполнено 20 из 50 монет | Q=80 в учебном примере; новое P_BE и стресс-защита. |
| T10 | TP1 fill совпал с hard stop и отменой TP2 | Прежде отмена/сверка, затем одна SELL на новый Q. |
| T11 | Сразу после TP1 нет bids | Нет обещанного нуля; аварийный путь и фактический остаток. |
| T12 | TP1 или TP2 после округления ниже minNotional | Предварительный запрет/утверждённая альтернативная TP-схема. |
| T13 | Появился дублированный trade/WS-order fill | Ни двойного BUY, ни двойного уменьшения Q. |
| T14 | Взяты разные комиссии: quote/base/другой токен | Верный Q/C/R и конечный PnL. |
| T15 | Все TP частично исполнены; остаток пылевой | `RESIDUAL_OPEN/DUST`, без ложного CLOSED. |
| T16 | RT-подобный скачок с быстрым откатом | Сохранить сделки только по реальным допустимым ценам/глубине. |
| T17 | LALA-подобный cap 30010 и успех `/order/test` | Есть capEvidence, нет ложного release от order/test. |
| T18 | Одновременно запущены A и B в REPLAY | Раздельные портфели, одинаковая лента, сравнимые метрики. |
| T19 | FAST failed; CONFIRMED eligible в LIVE | Нет скрытого переключения / второго BUY. |
| T20 | Критический fallback вернул неизвестный статус | Reconcile/RESIDUAL, запрет повторного SELL без проверки. |

**Критерии приёмки:** тесты T01–T20 зелёные; ноль дублей реальных ордеров; ledger и фактические суммы баланса согласованы; все partial TP корректно пересчитывают общую защиту; ни одно `CLOSED` не содержит Q>0; REPLAY детерминирован и воспроизводит исходные решения; в PAPER измерены задержки, слippage и незакрытые остатки; торговля LIVE остаётся выключенной по умолчанию до отдельных результатов.

## 16. Компоненты и интерфейсы разработчика

`CapDetector` → capEvidence; `ReleaseDetector` → CAP_RELEASED; `MarketBook` → согласованные снимки bid/ask; `EntryArbiter` → выбор FAST/CONFIRMED; `FastEntry`/`ConfirmedEntry` → ENTRY_ALLOWED/SKIP; `SlippageEngine` → buyVWAP/exitVWAP/stress; `OrderExecutor` + `OrderReconciler` → всё жизненное состояние ордеров; `FillLedger` → C/R/Q; `TotalPositionPnLGuard` → P_BE/P_LOCK/protection; `ExitManager` → TP/stop/urgent/fallback; `ReplayRunner` → сравнение и отчёты; `AuditLogger` → необрезанная последовательность событий.

**Схемы:** общая карта действий, подробная схема FAST, подробная схема CONFIRMED и схема управления остатком/проскальзыванием/выходом. Все диаграммы — часть пакета исходных требований, а при неоднозначности текстовые инварианты ордеров и ledger из разделов 7–11 имеют приоритет.

## 17. Источники и границы достоверности

- Предоставленные пользователем документ исходной стратегии, изображение исходной торговой логики, исторические архивы листингов и ранее оформленное ТЗ CAP BREAKOUT. Из них взяты существующие TP, TIME/BE/FAST STOP, aggressive LIMIT и проектный веб-fallback; запреты ложного CAP-сигнала и кейсы для REPLAY.

- Буфер 0.5%, защитная цель 0/+0.5%, окна входа, типы приоритета и условия стабилизации — **проектные предложения для тестирования**, не расчётный win rate и не обещание исполнения либо прибыли.
