# Решения по вопросам к ТЗ v2.1

Клиент ответил на документ «Вопросы по ТЗ: бот листингов MEXC v2.1» 12.10.2026 (`вопрос.docx` из Telegram), а на 7 уточнений — 15.10.2026. Открытых вопросов к клиенту нет, но решение от 19.10 (веб-канал для листингов с закрытым API, см. «Архитектура») меняет согласованные A1/A2 — клиенту нужно сообщить. Номера — как в документе с вопросами, в скобках — пометки ⚠Вn из [flowchart.md](flowchart.md). Пометка «(наше)» — решение разработчика, которое клиент не обсуждал.

Проверено по API 12.10.2026: `GET /api/v3/mxDeduct/enable` → `mxDeductEnable = false`; `GET /api/v3/tradeFee` → maker 0 %, taker 0.05 %. Данные по листингам — в [zhurnal_rabot.md](zhurnal_rabot.md).

## Архитектура

- **A1, A2 (В11). Бот работает только через официальный API, браузера с логином нет.** Вход, все выходы и критическая продажа идут через API. Вопрос A2 про логин, 2FA и сессию на сервере отпал.
- **A1. Если API для пары закрыт — листинг пропускается** (`SKIP_API_CLOSED` + алерт). Из четырёх записанных листингов API был закрыт на одном: на BORDR (Launchpad + Assessment) ордера получали `10007` примерно 45 мин, при этом `apiAllowed = false` в `exchangeInfo` держался около часа после `status = 1`. Правила:
  - если на момент окна входа у пары `apiAllowed = false`, бот даёт SKIP;
  - если BUY получил `10007` при `apiAllowed = true`, бот даёт SKIP на весь листинг без повторов (наше). На BORDR, пока API был закрыт, проходили 10–20 % ордеров. Поэтому вход при «мигающем» API может оставить позицию, из которой не получится выйти.
- **Изменение от 19.10.2026: для листингов с закрытым API добавляется веб-канал, вариант B.** Решение разработчика после разбора BORDR; правила A1/A2 выше (SKIP и «без браузера») для таких листингов заменяются, **клиенту нужно сообщить**.
  - Официальный API остаётся основным каналом. Веб-канал используется только когда пара закрыта для API (`apiAllowed = false` или `10007`).
  - **Вариант B: браузер без заполнения формы.** На сервере Playwright (Chromium) держит залогиненную сессию MEXC на открытой странице пары. Ордер отправляется вызовом функции самого сайта, которая собирает запрос `POST https://www.mexc.com/api/platform/spot/order/place` с полями `p0`/`k0`/`chash`/`mhash`/`mtoken` (их формирует защитный JS сайта, поэтому чистые HTTP-запросы не подходят, а Akamai отвечает 403). Ожидаемая задержка 100–300 мс против 0,5–2 с у заполнения формы (вариант C, как в v1).
  - Отвергнуты: A — пропускать такие листинги (теряем Launchpad/Assessment); C — форма v1 (медленно, хрупко); D — чистые запросы с реверсом шифрования `p0`/`k0` (самое хрупкое, нарушает правила MEXC).
  - Что нужно сделать: найти в JS сайта функцию отправки ордера и проверить её вызов из `page.evaluate`; решить, как поддерживать логин на сервере (2FA, срок жизни сессии, вопрос A2 снова открыт); замерить задержку веб-канала на следующем листинге с закрытым API.
  - Риски: обновление сайта ломает вызов; сессия слетает; автоматизация сайта нарушает правила MEXC (риск ограничений аккаунта).
- **A3 (В13). Источник листингов — парсер из v1.** Код: `CryptoTrading/ListingInfo.cs` и `MXC/MxcListing.cs`. Парсер берёт ссылки на пары MEXC со страницы tgstat.ru/channel/@ListingCryptoCoin, пропуская посты с 📌 и стейблкоины. Время старта он читает из таймера на странице пары (`span[class^='countDown_deadline__']`, Playwright без логина). Второй источник — наблюдатель exchangeInfo (status ≠ 1). Он видит пару за сутки, а момент открытия ловит по status = 1.
- **A4 (В13). Размер входа и бюджет.**
  - `orderUSDT` фиксирован в конфиге.
  - `botBudgetUSDT` — общий бюджет бота, в пределах которого можно открывать сделки. Вход разрешён, если стоимость открытых позиций + orderUSDT ≤ botBudgetUSDT и свободный USDT ≥ orderUSDT. Убытки бюджет не уменьшают (наше): такой лимит потерь клиент не захотел (`dailyLossLimitUSDT = null`).
  - Одновременно открыта не больше одной позиции (`maxOpenPositions = 1`).
  - Алерты идут в Telegram.

## Вход

- **B1 (В1).** Фильтры проверяются на каждом тике (100 ms) до конца `tradeWindowSec`. Вход — на первом тике, где все фильтры прошли. Окончательный SKIP — только когда окно истекло. В лог пишутся первая и последняя причины SKIP.
- **B2 (В2).** На тике, где фильтры прошли, бот запоминает `decisionAsk` и считает `buyLimitPrice` от него. Если свежий ask перед отправкой выше `decisionAsk × (1 + buyAggressiveCapPct)`, бот даёт `SKIP_PRICE_MOVED_BEFORE_SEND`.
- **B3 (В12).** Зоны depthBid считаются от bestBid, зоны depthAsk — от bestAsk, а не от midPrice, как в примерах ТЗ.
- **B4.** `hardMaxSpreadPct = 1.5` — верхняя граница для проверки конфига: при `maxSpreadPct > hardMaxSpreadPct` бот не стартует. Рабочий порог входа — `maxSpreadPct = 1.2`.
- **E2 (В14). Вариант клиента.** На каждом тике `buyLimitPrice` и `qty = floorToStep(orderUSDT / buyLimitPrice, qtyStep)` считаются от текущего bestAsk ещё до фильтра exitVWAP. Этот bestAsk станет `decisionAsk`, если тик пройдёт фильтры. exitVWAP считается для этого `qty`. BUY отправляется только после всех фильтров.

## Сопровождение позиции

- **C1 (В3).** Условие `elapsedSec ≥ X` проверяется на каждом тике, начиная с X. «Один раз» относится к самому выходу.
- **C2.** Порог −0.3 % на 3-й секунде — намеренный фильтр быстрого импульса. Время и порог задаются в конфиге и подбираются тестами.
- **C3 (В4). `TIME_STOP_NO_MOMENTUM`.** При `elapsedSec ≥ 8` бот выходит, если TP1 не исполнен и exitVWAP за последние `momentumLookbackSec` вырос меньше чем на `momentumMinGrowthPct`. Новые параметры: `momentumLookbackSec = 2` (от клиента) и `momentumMinGrowthPct = 0` (наше: «не вырос» означает рост ≤ 0).
- **C4 (В15).** Триггеры проверяются на тике в таком порядке, срабатывает первый: DEPTH_DISAPPEARED → HARD_STOP → FAST_WINDOW_DUMP → FAST_DROP_STOP → BREAK_EVEN_STOP → TIME_STOP_NEGATIVE → TIME_STOP_NO_EDGE → TIME_STOP_NO_MOMENTUM → MAX_HOLD_TIME. FAST_WINDOW_DUMP действует всё время удержания.
- **C5 (В8).** Пока стакан пересинхронизируется, стопы заморожены, но не дольше `bookResyncMaxFreezeMs = 1000`. Если стакан не восстановился, начинается срочный выход по bestBid из REST.

## Выход и остатки

- **Критический выход (A2, D4, D6; В7, В11) — MARKET SELL через API вместо веб-формы `RequestSellOrderMinPrice()`.** Проверено 15.10 на CHOMPUSDT (~T+20 мин): MARKET BUY и MARKET SELL исполняются сразу. LIMIT SELL дальше ±20 % от рынка API отклоняет (`30087`, `PERCENT_PRICE_BY_SIDE`), поэтому «лимитку около нуля» через API поставить нельзя.
  - На всех записанных листингах (WFI, BORDR/USDT, BORDR/USD1, CHOMP) MARKET был в `orderTypes` с самого начала.
  - Клиент просит убедиться, что так будет всегда. Наблюдатель делает MARKET-тест на каждом листинге (`--market-test`).
  - Если у пары нет MARKET в `orderTypes`, вход запрещён (`SKIP_NO_MARKET_ORDER`, наше): без MARKET у позиции нет критического выхода.
- **D1 (В6).** Оплата комиссии в MX выключена, поэтому комиссия BUY списывается в купленной монете. Объём позиции = Σ fill − комиссия в монете (по полю `commissionAsset` каждого fill), с округлением вниз по `qtyStep`. Если MX-оплату включат, логика не меняется: комиссия в MX просто не вычитается.
- **D2 (В5).** Если позиция меньше 2 × minNotional, ставится один TP на весь объём. С остатком меньше minNotional поступаем как в D4.
- **D3 (В5). `BUY_PARTIAL_TOO_SMALL`.** Если стоимость ≥ minNotional, бот сразу ставит срочный LIMIT SELL. Если меньше — DUST и запись в лог.
- **D4 (В7). Мелкий остаток.** Бот пробует продать остаток через API (MARKET SELL). Если биржа отклоняет ордер из-за минимальной суммы (`30002`, минимум 1 USDT), остаток помечается DUST. Каждый такой случай пишется в лог отдельным событием (qty, стоимость по bestBid, minNotional, ответ биржи). Порог 1.2 USDT от веб-формы больше не нужен.
- **D5 (В10).** Если критический SELL не прошёл, цикл повторяется через `criticalRetryCycleDelayMs = 1000`, пока позиция не закрыта или не вмешался человек. После первого неудачного цикла — алерт в Telegram. Новые входы на это время запрещены.
- **D6 (В16).** Таймаут веб-формы `criticalCreateResponseTimeoutMs = 10000` больше не нужен. Вместо него таймаут ответа API на критический SELL `criticalOrderResponseTimeoutMs`, по умолчанию 2000 ms (наше; на листингах API отвечал за 33–76 ms). Клиент хотел подобрать значение по факту, поэтому время каждого ответа пишется в лог.
- **E1.** Цены TP округляются вверх до tickSize, цены срочных выходов — вниз.

## Комиссии

В примере ТЗ `buyFeePct = sellFeePct = 0.1`, а на аккаунте taker 0.05 %, maker 0 %. Клиент опасается, что запрос комиссии задержит покупку. Поэтому:

- комиссия символа запрашивается через `GET /api/v3/tradeFee` в фоне, пока бот ждёт открытия пары; запрос повторяется, пока не ответит. В момент покупки запроса нет;
- если к началу окна входа ответа нет, берётся значение из конфига;
- после BUY фактическая комиссия покупки берётся из fill-ов (поле `commission`).

## Осталось проверить на листингах (не вопросы клиенту)

- MARKET в первые минуты листинга, особенно там, где API на старте закрыт или «мигает». Тест включён в наблюдатель.
- Отвечает ли `tradeFee` по паре до открытия.
