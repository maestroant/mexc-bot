## Архитектура

- **A1, A2 (В11). Бот работает только через официальный API, браузера с логином нет.** Вход, все выходы и критическая продажа идут через API. Вопрос A2 про логин, 2FA и сессию на сервере отпал.
- **A1. Если API для пары закрыт — листинг пропускается** (`SKIP_API_CLOSED` + алерт). Из четырёх записанных листингов API был закрыт на одном: на BORDR (Launchpad + Assessment) ордера получали `10007` примерно 45 мин, при этом `apiAllowed = false` в `exchangeInfo` держался около часа после `status = 1`. Правила:
  - если на момент окна входа у пары `apiAllowed = false`, бот даёт SKIP;
  - если BUY получил `10007` при `apiAllowed = true`, бот даёт SKIP на весь листинг без повторов (наше). На BORDR, пока API был закрыт, проходили 10–20 % ордеров. Поэтому вход при «мигающем» API может оставить позицию, из которой не получится выйти.
- **23.10.2026: только официальный API.** Веб-канал (вариант B, решение 19.10) отменён, A1 и A2 снова действуют без исключений. Неофициальный API сайта (`www.mexc.com/api/platform/...`), автоматизация браузера и чтение страниц MEXC в боте не используются. Клиент 22.10 сам предлагал пропускать такие листинги, если веб-API себя не покажет. Закрытый API за 15 листингов встретился дважды: BORDR 14.10 и KIMCHI 21.10. Материалы по веб-каналу перенесены в [_trash/doc/veb_kanal.md](../_trash/doc/veb_kanal.md).
- **A3 (В13). Источник листингов — парсер из v1.** Код: `CryptoTrading/ListingInfo.cs` и `MXC/MxcListing.cs`. Парсер берёт ссылки на пары MEXC со страницы tgstat.ru/channel/@ListingCryptoCoin, пропуская посты с 📌 и стейблкоины. Время старта он читает из таймера на странице пары (`span[class^='countDown_deadline__']`, Playwright без логина). Второй источник — наблюдатель exchangeInfo (status ≠ 1). Он видит пару за сутки, а момент открытия ловит по status = 1.
  - **Заменено 23.10: источник — официальный `exchangeInfo`.** Парсер v1 читает tgstat.ru и таймер на странице пары, а это не API. Сам канал @ListingCryptoCoin — бот, который следит за API бирж: он публикует пару в пределах минуты от нашего наблюдателя, без времени старта, и пропустил 3 листинга из 13. Время старта отдаёт `exchangeInfo` в поле `firstOpenTime`: оно появляется за 5–85 мин до открытия и совпадает с открытием до секунды. Будущую пару видно раньше, по `status = 2`. Анонсы листингов уходят в Telegram (журнал, 23.10). Клиенту сообщить.
- **A4 (В13). Размер входа и бюджет.**
  - `orderUSDT` фиксирован в конфиге.
  - `botBudgetUSDT` — общий бюджет бота, в пределах которого можно открывать сделки. Вход разрешён, если стоимость открытых позиций + orderUSDT ≤ botBudgetUSDT и свободный USDT ≥ orderUSDT. Убытки бюджет не уменьшают (наше): такой лимит потерь клиент не захотел (`dailyLossLimitUSDT = null`).
  - Одновременно открыта не больше одной позиции (`maxOpenPositions = 1`).
  - Алерты идут в Telegram.

## Вход

- **B1 (В1).** Фильтры проверяются на каждом тике (100 ms) до конца `tradeWindowSec`. Вход — на первом тике, где все фильтры прошли. Окончательный SKIP — только когда окно истекло. В лог пишутся первая и последняя причины SKIP.
- **B2 (В2).** На тике, где фильтры прошли, бот запоминает `decisionAsk` и считает `buyLimitPrice` от него. Если свежий ask перед отправкой выше `decisionAsk × (1 + buyAggressiveCapPct)`, бот даёт `SKIP_PRICE_MOVED_BEFORE_SEND`.
- **B3 (В12).** Зоны depthBid считаются от bestBid, зоны depthAsk — от bestAsk, а не от midPrice, как в примерах ТЗ.
- **B4.** `hardMaxSpreadPct = 1.5` — верхняя граница для проверки конфига: при `maxSpreadPct > hardMaxSpreadPct` бот не стартует. Рабочий порог входа — `maxSpreadPct = 1.2`.
- **E2 (В14). Вариант клиента.** На каждом тике `buyLimitPrice` и `qty = floorToStep(orderUSDT / buyLimitPrice, qtyStep)` считаются от текущего bestAsk ещё до фильтра exitVWAP. Этот bestAsk станет `decisionAsk`, если тик пройдёт фильтры. exitVWAP считается для этого `qty`. BUY отправляется только после всех фильтров.

## Сопровождение позиции

- **C1 (В3).** Условие `elapsedSec ≥ X` проверяется на каждом тике, начиная с X. «Один раз» относится к самому выходу.
- **C2.** Порог −0.3 % на 3-й секунде — намеренный фильтр быстрого импульса. Время и порог задаются в конфиге и подбираются тестами.
- **C3 (В4). `TIME_STOP_NO_MOMENTUM`.** При `elapsedSec ≥ 8` бот выходит, если TP1 не исполнен и exitVWAP за последние `momentumLookbackSec` вырос меньше чем на `momentumMinGrowthPct`. Новые параметры: `momentumLookbackSec = 2` (от клиента) и `momentumMinGrowthPct = 0` (наше: «не вырос» означает рост ≤ 0).
- **C4 (В15).** Триггеры проверяются на тике в таком порядке, срабатывает первый: DEPTH_DISAPPEARED → HARD_STOP → FAST_WINDOW_DUMP → FAST_DROP_STOP → BREAK_EVEN_STOP → TIME_STOP_NEGATIVE → TIME_STOP_NO_EDGE → TIME_STOP_NO_MOMENTUM → MAX_HOLD_TIME. FAST_WINDOW_DUMP действует всё время удержания.
- **C5 (В8).** Пока стакан пересинхронизируется, стопы заморожены, но не дольше `bookResyncMaxFreezeMs = 1000`. Если стакан не восстановился, начинается срочный выход по bestBid из REST.

## Выход и остатки

- **Критический выход (A2, D4, D6; В7, В11) — MARKET SELL через API вместо веб-формы `RequestSellOrderMinPrice()`.** Проверено 15.10 на CHOMPUSDT (~T+20 мин): MARKET BUY и MARKET SELL исполняются сразу. LIMIT SELL дальше ±20 % от рынка API отклоняет (`30087`, `PERCENT_PRICE_BY_SIDE`), поэтому «лимитку около нуля» через API поставить нельзя.
  - На всех записанных листингах (WFI, BORDR/USDT, BORDR/USD1, CHOMP) MARKET был в `orderTypes` с самого начала.
  - Клиент просит убедиться, что так будет всегда. Наблюдатель делает MARKET-тест на каждом листинге (`--market-test`).
  - Если у пары нет MARKET в `orderTypes`, вход запрещён (`SKIP_NO_MARKET_ORDER`, наше): без MARKET у позиции нет критического выхода.
- **D1 (В6).** Оплата комиссии в MX выключена, поэтому комиссия BUY списывается в купленной монете. Объём позиции = Σ fill − комиссия в монете (по полю `commissionAsset` каждого fill), с округлением вниз по `qtyStep`. Если MX-оплату включат, логика не меняется: комиссия в MX просто не вычитается.
- **D2 (В5).** Если позиция меньше 2 × minNotional, ставится один TP на весь объём. С остатком меньше minNotional поступаем как в D4.
- **D3 (В5). `BUY_PARTIAL_TOO_SMALL`.** Если стоимость ≥ minNotional, бот сразу ставит срочный LIMIT SELL. Если меньше — DUST и запись в лог.
- **D4 (В7). Мелкий остаток.** Бот пробует продать остаток через API (MARKET SELL). Если биржа отклоняет ордер из-за минимальной суммы (`30002`, минимум 1 USDT), остаток помечается DUST. Каждый такой случай пишется в лог отдельным событием (qty, стоимость по bestBid, minNotional, ответ биржи). Порог 1.2 USDT от веб-формы больше не нужен.
- **D5 (В10).** Если критический SELL не прошёл, цикл повторяется через `criticalRetryCycleDelayMs = 1000`, пока позиция не закрыта или не вмешался человек. После первого неудачного цикла — алерт в Telegram. Новые входы на это время запрещены.
- **D6 (В16).** Таймаут веб-формы `criticalCreateResponseTimeoutMs = 10000` больше не нужен. Вместо него таймаут ответа API на критический SELL `criticalOrderResponseTimeoutMs`, по умолчанию 2000 ms (наше; на листингах API отвечал за 33–76 ms). Клиент хотел подобрать значение по факту, поэтому время каждого ответа пишется в лог.
- **E1.** Цены TP округляются вверх до tickSize, цены срочных выходов — вниз.

- **Ответ клиента от 22.10.2026 о запасном выходе.** MARKET SELL не всегда исполняется: `30083` (нет последней цены), `30010` (потолок цены на открытии), отмена без исполнения (bid дальше 5 % от последней цены — AXIS 21.10). Поэтому после MARKET SELL бот проверяет `executedQty` и остаток продаёт LIMIT-ом ниже bid. Клиент не хочет произвольных 2 %: отступ должен опираться на предел биржи. Предел биржи для LIMIT SELL — `PERCENT_PRICE_BY_SIDE`, `askMultiplierDown = 0.2` (цена не ниже 80 % от рыночной, иначе `30087`). Отступ — параметр конфига; значение по умолчанию согласовать с клиентом (открыто).

## Комиссии

В примере ТЗ `buyFeePct = sellFeePct = 0.1`, а на аккаунте taker 0.05 %, maker 0 %. Клиент опасается, что запрос комиссии задержит покупку. Поэтому:

- комиссия символа запрашивается через `GET /api/v3/tradeFee` в фоне, пока бот ждёт открытия пары; запрос повторяется, пока не ответит. В момент покупки запроса нет;
- если к началу окна входа ответа нет, берётся значение из конфига;
- после BUY фактическая комиссия покупки берётся из fill-ов (поле `commission`).

## BASELINE и MAIN_EARLY (решения клиента 03–04.11.2026)

- **BASELINE** — ТЗ v2.1 без изменений, контрольный вариант; фильтры дальше не смягчаем, временные стопы сохраняем.
- **MAIN_EARLY** — исследовательский ранний вход на листингах без потолка, только REPLAY и PAPER, в LIVE не переносить; параметры не подбирать под один листинг (EMYA). Проверяются комбинации признаков, без будущих данных:
  - окно 1 / 2 / 3 / 5 с от T0;
  - рост bestAsk ≤ +20 / +40 / +60 % от **первого действительного bestAsk синхронизированного двустороннего стакана** (основная опора); первая сделка — диагностическая опора для сравнения;
  - импульс за 100 / 250 / 500 мс: середина выросла, bestBid не упал, спред в пределах; строгий вариант — bestBid вырос хотя бы на шаг цены (рост середины не только от расширения спреда); истории на окно нет — импульс не подтверждён;
  - глубина bids к позиции; план 2 / 5 / 10 USDT; возраст стакана 100 / 250 / 500 мс;
  - постоянно: спред ≤ 3 %, весь план в asks до bestAsk +1 %, `estimatedExitSlippagePct` ≤ 1,5 %, стакан синхронизирован (иначе вход запрещён); `updatesPerSec` в первые секунды не проверяется.
- **Выходы MAIN_EARLY:** стандартный (как BASELINE); TP1 +2 % на 50 %, остаток — trailing 5 % от пика исполнимого bid-VWAP, защита общего netPnL +0,3 %, удержание до 30 с; то же без TIME_STOP_* для остатка после фактического TP1 (HARD_STOP, FAST_WINDOW_DUMP, FAST_DROP_STOP, DEPTH_DISAPPEARED, trailing, защита и maxHold действуют). При частичном TP1 — пересчёт проданного и остатка, без двух SELL на одно количество.
- **Деление позиции на TP** — по minNotional и qtyStep, а не по фиксированной сумме: если хоть одна часть с запасом на цену и комиссию не проходит ограничения биржи, — один TP на весь объём (наше: запас 10 %).
- **Комиссии** — фактические инструмента и аккаунта, maker и taker отдельно (exchangeInfo `takerCommission`/`makerCommission`; в LIVE — `tradeFee` в фоне).
- **Время:** одинаковые правила для REPLAY и PAPER. T0 = официальное время открытия (`firstOpenTime`, exchangeOpenTime); отдельно сохраняются первый действительный двусторонний стакан и первая сделка. Нет официального времени — T0 = первое из этих двух.
- **PAPER** — BASELINE, MAIN_EARLY, CAP BREAKOUT FAST / CONFIRMED / EARLY на одних данных, статистика раздельно.
- **Приоритет исследования (04.11)** — качество входа до первоначального рывка (особенно KAMIRAI): раздельно момент появления стакана, первой сделки и первого исполнимого BUY. Вывод клиента: ни BASELINE, ни MAIN_EARLY пока не имеют доказанного устойчивого преимущества; PAPER продолжаем для накопления наблюдений.

## Решения клиента 08.11.2026 и план работ

- **Вывод:** устойчивого преимущества нет ни у BASELINE v2.1, ни у MAIN_EARLY; главный приоритет — инфраструктурная неопределённость (VLX: REPLAY и PAPER разошлись), а не параметры. В LIVE ничего нового не переносить.
- **Trailing всей позиции** — включается, когда исполнимый bid-VWAP всего объёма ≥ фактическая средняя цена BUY +2 %; откат 5 % от максимума, защита +0,3 %, maxHold 30 с; после включения выключаются только временные стопы, HARD_STOP и аварийные защиты действуют. Порог +2 % не менять; другие — только новой предрегистрацией.
- **Защита +0,3 %** — не с момента покупки: разрешена после фактического TP1 (частичный TP) или после включения trailing (trailing всей позиции), и только когда риск-скорректированный общий netPnL (фактическая стоимость BUY, комиссии, реализованные частичные SELL, исполнимый exitVWAP остатка, ожидаемая комиссия SELL, резерв проскальзывания — один раз) достиг +0,3 %. Включившись, не выключается; прибыль не гарантирует. Из нескольких защит — более строгая; аварийные выходы — в приоритете.
- **Строгий импульс** — как есть (bestBid ≥ +1 шаг, midPrice вырос, стакан синхронизирован, истории на окно достаточно). Условие про расширение спреда при росте bestBid выполняется автоматически — не считать отдельным фильтром. Вариант ΔbestBid ≥ 0,5 × ΔmidPrice — позже, новой предрегистрацией.
- **Качество данных** — восстанавливать время только при доказанных остановках записи > 1 с; задержки 200–500 мс не исправлять. Раздельно ENTRY_DATA_VALID (повреждённый или восстановленный интервал в окне T0 − 2 с … конец окна входа → результат вне основной статистики ранних входов) и EXIT_DATA_VALID (потерянные события или нарушенная последовательность стакана после входа, способные повлиять на TP, trailing, стоп или SELL → выход недостоверен). Выходы сравнивать на общей допустимой выборке; корректную короткую сделку не исключать из-за более позднего сбоя. Хранить sendTime, localReceiveTime, decisionTime, синхронизацию стакана, разрывы, восстановленные интервалы, причины недостоверности, качество входа и выхода. KAMIRAI и GANG — в архиве, ранние интервалы для доказательства MAIN_EARLY не использовать.
- **Предрегистрация** — VLX не входит в PR-2026-11-06 (PAPER шёл со старым набором), но остаётся в исследовательском наборе как пример расхождения. Первое событие оценки — следующий листинг, где правила и ядро были активны до открытия. Для каждого события хранить идентификаторы конфигурации, версии кода, модели исполнения и комиссий. Ничего задним числом.
- **План по фазам:**
  - **P0** (критично) — причина расхождения VLX: покадровое сравнение записи и PAPER, начало WS-подключений и подписок, порядок REST snapshot и delta, разрывы и ресинхронизация, задержки очередей и цикла событий, блокирующие операции (Telegram, логирование), не даёт ли REPLAY данные раньше localReceiveTime, повторное воспроизведение. Закрыта, когда причина установлена, на одинаковом потоке REPLAY и PAPER решают одинаково, различия живых соединений измерены и объяснены, недостоверные по времени результаты исключены, блокирующих операций нет. Одного совпавшего повторного прогона недостаточно.
  - **P1** — аудит модели исполнения: LIMIT BUY по asks с задержкой и ценовым ограничением, частичные BUY и отмена остатка, очередь TP и частичные SELL, порядок отмены TP / защитного выхода / сверки остатка, комиссии и ограничения биржи, DUST, повторные SELL, неизвестный статус ордера, запрет двойной продажи, ухудшение стакана между сигналом и приходом ордера; `RequestSellOrderMinPrice()` — обязательный резерв для будущего LIVE, REPLAY её не моделирует.
  - **P2** — зафиксировать алгоритмы и предрегистрацию: BASELINE без изменений; MAIN_EARLY — только заранее зафиксированный набор; CAP BREAKOUT FAST, CONFIRMED, EARLY — раздельно. Конфигурация, версия кода, версия исполнения, комиссии, правила качества — для каждой стратегии.
  - **P3** — PAPER и отчёт в Telegram после каждого листинга (тип события, первый стакан и сделка, задержки, совпадение REPLAY/PAPER, сигналы и пропуски, причины, объёмы BUY/SELL, netPnL и остаток, MFE/MAE, худшая сделка и просадка, причины выходов, без лучшего и двух лучших, качество данных). Не считать комбинации одного листинга независимыми сделками.
  - **P4** — итоговая оценка по каждой стратегии: CONTINUE RESEARCH / REDESIGN / STOP / CANDIDATE FOR LIVE REVIEW (не разрешение LIVE).
- **Правила изменений:** BASELINE не менять без согласования; не оптимизировать задним числом; расхождения REPLAY/PAPER — отдельные технические события; на недостоверных данных исполнение не подтверждено; MAIN_EARLY и CAP BREAKOUT EARLY — не в LIVE; PAPER не доказывает место в очереди. Общий торговый механизм для REPLAY, PAPER и LIVE, исполнение и отчётность — раздельно.

- **Формат отчёта:** по каждому пакету статус NOT_STARTED / IMPLEMENTED / TESTED_OFFLINE / DEPLOYED / VERIFIED_LIVE / BLOCKED, commit и fingerprint, файлы, команды и результаты, число реально обработанных записей, before/after, остаточный риск, нужные разрешения; не переписывать исторический отчёт. **P0 OPEN; P1 — тест-планы; P2–P4 не начаты; LIVE STRATEGY BLOCKED.**

## Пересмотр клиента 19.11.2026 (v2) после блок-схем — заменяет порядок пакета I

- **Главное:** не ждать активного листинга, не оптимизировать 186 веток ради плюса, не закрывать P0 по совпадению на спокойных рынках. Следующий артефакт — **Opportunity & Latency Audit**: где исчезает возможность — (а) сигнала в данных не было; (б) сигнал был, но поздно дошёл до PAPER; (в) решение вовремя, но ордер не исполнился бы; (г) исполненная стратегия убыточна. P0 OPEN, LIVE STRATEGY BLOCKED.
- **Задержки:** два бюджета по монотонной шкале — `exchange_event → receive → timestamp → queue → book_valid → decision` и `decision → submit → accepted/rejected → fill/cancel → protected_exit`; мерило — сколько потенциально исполнимых сигналов теряется на каждом этапе. Memo не лечит задержку WS.
- **PAPER = REPLAY — матрица 2×2:** (А) детерминированность ядра — PAPER A и REPLAY(A) на одном потоке обязаны совпасть; (Б) разница источников Recording / A / B — сравнивать первое событие и момент доступности, а не требовать нуля. Shadow-consumer на копии одного сырого потока (без новых WS) плюс независимые A/B. Нагрузочные инъекции (задержки 20/30/200/800 мс, всплески, разрывы, паузы CPU) — сейчас, на исторических потоках; не заменяют активный листинг.
- **Время знания справочника:** у каждой версии `valid_from` и `known_at`, источник; в движок — только версия, известная к кадру; переносы (KOR) не меняют прошлых решений. **Тест неизменности префикса по метаданным** (exchangeInfo, KNOWN_CAPS, полоса, шаги, комиссии, статусы API). `LATE_JOIN` — fail-closed.
- **CAP:** частично наблюдаемое состояние; две когорты — валидирующая (PIT-известные статусы) и эксплуатационная intention-to-observe (все заранее зарегистрированные листинги, включая CAP_UNCERTAIN, API unavailable, невалидный стакан, нулевые входы, по заранее определённой политике UNKNOWN). Манифест — независимые измерения: `data_quality`, `knowledge_provenance`, `cap_evidence_as_of`, `api_access_as_of`, `book_quality_as_of`, `analysis_cohort`, `reason_not_traded`. Воронка: обнаружены → записаны → пригодны → сигнал → API готов → ордер мог быть подан → исполнился → закрылся (абсолютные числа, доли, причины).
- **Знаменатели:** развести сконструированные ветки / ветки с допустимым сигналом / ветки с завершёнными сделками; единица вывода — независимый листинг; по каждой заранее зафиксированной конфигурации — воронка, издержки, net PnL, хвосты, интервалы.
- **Audit v1** — по каждому листингу и 1–3 заранее заявленным конфигурациям (BASELINE обязателен + ≤ 2 exploratory): Market opportunity / Arrival / Computation / Orderability / Fillability / Economics; три отчёта — as-recorded (что видел PAPER A), same-feed deterministic replay, latency-sensitivity counterfactual (feed delay и computation delay отдельно, диагностика).
- **Блок I сейчас:** (1) LATE_JOIN / OPEN_TIME_UNCONFIRMED + причинная подача exchangeInfo с known_at + тест неизменности префикса по метаданным; (2) манифест event- и listing-level, CAP_UNCERTAIN с ценами/моментами; (3) Audit v1 без изменения PR-2026-11-06 и рейтингов; (4) регрессия 32 / 8 / 2 + все отрицательные self-test, хеши источников и отчётов. Приёмка: ни одного ложного T0; изменения после T не меняют решений до T; CAP_UNCERTAIN не «без потолка»; известен знаменатель 68 и каждое исключение; при сомнении UNKNOWN. **Блок II** — наблюдение активного листинга (иначе NOT_OBSERVED). **Блок III** — после I, отдельными версиями: memo canary, группировка журнала, внешний heartbeat (только оповещение и сверка), steal против BurstCapacity; смена сервера — только при доказанной доле потерь из-за вычислений. **Блок IV** — P1–P4 через отдельные ворота; при отсутствии сигналов в хорошем потоке — зафиксировать отсутствие edge, не подгонять фильтры.
- **Отчёт по блоку I:** T0 до/после и отрицательные тесты, known_at / prefix invariance; воронка когорт и знаменатель 68, VLX и WASTED; Audit по листингам; реестр версий (git, raw SHA, normalized, параметры, справочник, манифест, версии отчётного инструмента); регрессия и объяснение каждой разницы; статусы TESTED_OFFLINE / OBSERVED_LIVE / UNVERIFIED / BLOCKED раздельно.
